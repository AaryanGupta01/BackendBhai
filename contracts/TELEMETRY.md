## 1. Trace Model

A trace represents a single end-to-end request flow across all services.

```typescript
interface Trace {
  traceId: string;          // 32-character hex string (128-bit)
  rootService: string;      // Name of the service that received the initial request
  method: string;           // HTTP method of the root request
  path: string;             // URL path of the root request
  statusCode: number;       // HTTP status code of the root response
  durationMs: number;       // Total trace duration in milliseconds
  timestamp: string;        // ISO 8601 timestamp of trace start
  hasError: boolean;        // Whether any span in the trace has an error
  services: string[];       // Unique list of service names involved
  requestBody?: object;     // Request body of the root span (if captured)
  responseBody?: object;    // Response body of the root span (if captured)
  requestHeaders?: Record<string, string>;  // Request headers (redacted)
  responseHeaders?: Record<string, string>; // Response headers (redacted)
}
```

### Trace ID Format

- **Length:** 32 hexadecimal characters (128 bits)
- **Generated by:** OpenTelemetry SDK (auto-generated for root spans)
- **Propagated via:** W3C `traceparent` header
- **Example:** `5b8efff798038103d269b633813fc60c`

### Traceparent Header Format

```
traceparent: 00-<trace-id>-<parent-span-id>-<trace-flags>
```

Example:
```
traceparent: 00-5b8efff798038103d269b633813fc60c-eee19b7ec3c1b174-01
```

| Field | Description |
|-------|-------------|
| `00` | Version (always `00`) |
| `trace-id` | 32-char hex trace ID |
| `parent-span-id` | 16-char hex parent span ID |
| `trace-flags` | Trace flags (`01` = sampled) |

## 2. Span Model

A span represents a single operation within a trace.

```typescript
interface Span {
  spanId: string;            // 16-character hex string (64-bit)
  parentSpanId: string | null;  // Parent span ID (null for root span)
  traceId: string;           // Reference to parent trace
  service: string;           // Service name (from OTel Resource)
  operation: string;         // Span name (e.g., "POST /api/orders")
  kind: SpanKind;            // "server" | "client" | "internal"
  startTimestamp: string;    // ISO 8601 timestamp
  durationMs: number;        // Duration in milliseconds
  status: SpanStatus;        // "OK" | "ERROR"
  statusCode?: number;       // HTTP status code (for HTTP spans)
  attributes: Record<string, string | number | boolean>;  // Span attributes
  events: SpanEvent[];       // Span events (exceptions, messages)
}
```

### Span Kind

| Kind | Description | Example |
|------|-------------|---------|
| `server` | Inbound HTTP request | API Gateway receives POST /api/orders |
| `client` | Outbound HTTP request | Payment Service calls Mock Payment API |
| `internal` | Internal business logic | Order processing span |

### Span Status

| Status | Description |
|--------|-------------|
| `OK` | Operation completed successfully |
| `ERROR` | Operation failed (exception recorded) |

### Span Events

```typescript
interface SpanEvent {
  name: string;              // Event name (e.g., "exception")
  timestamp: string;         // ISO 8601 timestamp
  attributes: Record<string, string | number | boolean>;
}
```

## 3. Log Model

A log event is correlated to a trace via `traceId` and optionally `spanId`.

```typescript
interface LogEvent {
  timestamp: string;         // ISO 8601 timestamp
  level: LogLevel;           // "debug" | "info" | "warn" | "error"
  service: string;           // Service name
  message: string;           // Log message
  traceId: string;           // Correlated trace ID
  spanId?: string;           // Correlated span ID (optional)
  attributes: Record<string, string | number | boolean>;
}
```

### Log Levels

| Level | Description |
|-------|-------------|
| `debug` | Detailed debugging information |
| `info` | General information messages |
| `warn` | Warning messages |
| `error` | Error messages |

## 4. HTTP Attributes

Spans representing HTTP operations use these attributes:

### HTTP Server Spans (inbound requests)

| Attribute | Type | Description | Example |
|-----------|------|-------------|---------|
| `http.request.method` | string | HTTP method | `POST` |
| `url.path` | string | URL path | `/api/orders` |
| `url.query` | string | Query string | `?page=1` |
| `http.response.status_code` | number | Response status code | `201` |
| `network.protocol.version` | string | HTTP version | `1.1` |
| `server.address` | string | Server hostname | `api-gateway` |
| `server.port` | number | Server port | `3000` |

### HTTP Client Spans (outbound requests)

| Attribute | Type | Description | Example |
|-----------|------|-------------|---------|
| `http.request.method` | string | HTTP method | `POST` |
| `url.full` | string | Full URL | `http://mock-payment-api:4000/charges` |
| `url.path` | string | URL path | `/charges` |
| `http.response.status_code` | number | Response status code | `200` |
| `server.address` | string | Target hostname | `mock-payment-api` |
| `server.port` | number | Target port | `4000` |

### Internal vs External Call Detection

A call is considered **external** if:
- `server.address` does NOT match any known internal service name
- Known services: `api-gateway`, `auth-service`, `order-service`, `payment-service`

## 7. Request/Response Bodies

### Capture Mechanism

Request and response bodies are captured via **shared Express middleware** in `packages/instrumentation/`.

**Request Body Capture:**
- Middleware intercepts `req.body` after Express parsing
- Adds as span attribute: `custom.http.request.body` (JSON stringified)
- Maximum size: 10KB (larger bodies are truncated)

**Response Body Capture:**
- Middleware intercepts `res.json()` output
- Adds as span attribute: `custom.http.response.body` (JSON stringified)
- Maximum size: 10KB (larger bodies are truncated)

### Storage

Request and response bodies for the **root span** (the initial HTTP request) are stored in the `traces` table:
- `traces.request_body` — JSON string of the request body
- `traces.response_body` — JSON string of the response body
- `traces.request_headers` — JSON object of request headers (redacted)
- `traces.response_headers` — JSON object of response headers (redacted)

## 8. Trace-Context-Aware Logging

### Console.log Monkey-Patch

The shared instrumentation module patches `console.log` and `console.error` to automatically inject trace context:

```typescript
// Patches console.log to inject:
// - trace_id (from current OTel context)
// - span_id (from current OTel context)
// Output format: JSON with trace context injected
```

**Before patch:**
```
console.log("Order created for user-42")
```

**After patch (actual output):**
```json
{
  "message": "Order created for user-42",
  "trace_id": "5b8efff798038103d269b633813fc60c",
  "span_id": "abc123def456",
  "service": "order-service",
  "level": "info",
  "timestamp": "2026-09-06T12:00:00.100Z"
}
```

**Why:** OTel auto-instrumentation does NOT automatically attach trace context to `console.log` output. Without this monkey-patch, logs would have no `trace_id` and would not appear in the Logs tab.

### Logger Usage

All demo services should use `console.log` and `console.error`. The monkey-patch handles trace context injection automatically. No custom logger is required.

## 9. Redaction Rules

### Layer 1: OTel Collector (Header Redaction)

The Collector's `attributes` processor redacts sensitive headers before export:

| Header | Action | Replacement |
|--------|--------|-------------|
| `authorization` | update | `**REDACTED**` |
| `cookie` | update | `**REDACTED**` |
| `x-api-key` | update | `**REDACTED**` |
| `x-auth-token` | update | `**REDACTED**` |

### Layer 2: DevTools Server (Body Redaction)

The DevTools server redacts sensitive fields in request/response bodies before storage:

| Field Pattern | Action | Replacement |
|---------------|--------|-------------|
| `password` | replace value | `***` |
| `token` | replace value | `***` |
| `secret` | replace value | `***` |
| `credit_card` | replace value | `***` |
| `ssn` | replace value | `***` |

### Redaction Scope

- Headers are redacted at the Collector level (before export)
- Body fields are redacted at the server level (before storage)
- Span attributes are NOT redacted (except via Collector for headers)
- For hackathon demo with fake data, redaction completeness is not critical

## 10. OTel Collector Pipeline

### Pipeline Configuration

```
Receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

Processors:
  batch:
    timeout: 1s
    send_batch_size: 200
  attributes/redact:
    actions:
      - key: authorization
        action: update
        value: "**REDACTED**"
      - key: cookie
        action: update
        value: "**REDACTED**"
      - key: x-api-key
        action: update
        value: "**REDACTED**"

Exporters:
  otlphttp:
    endpoint: http://devtools-core:4001
    traces_endpoint: http://devtools-core:4001/api/v1/telemetry/traces

Service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, attributes/redact]
      exporters: [otlphttp]
```

### Export Protocol

- **Collector → DevTools Server:** OTLP HTTP (JSON format)
- **DevTools Server receives:** `ExportTraceServiceRequest` JSON
- **No gRPC receiver** in DevTools server (per pre-development audit recommendation)

### Data Flow

```
Simulated Backend → OTLP gRPC (:4317) → OTel Collector → OTLP HTTP → DevTools Server → PostgreSQL
```
